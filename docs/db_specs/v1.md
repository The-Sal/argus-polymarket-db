# APDB On-Disk Format — v1

`format_version: 1`. Adds a reserved metadata record at line 0, making the
database file self-describing about its own age and format — the on-disk
counterpart to the boot-time TTL check described below. Builds on
[v0](./v0.md); everything about record shape, compaction, and atomic rewrite
there still applies to line 1 onward.

## Layout

```
{"__apdb_meta__":true,"format_version":1,"built_at_unix":1755000000}\n
{"ticker":"...", "endDate":"...", ...}\n
{"ticker":"...", "endDate":"...", ...}\n
...
```

- **Line 0 — meta record.** Written by `full_crawl_and_compact`
  (`src/refresh.rs`) before any crawled or carried-forward record, on
  *every* compaction (initial crawl, periodic refresh, and the new
  stale-at-boot refresh alike). Fields:

  | Field             | Type   | Meaning                                                                 |
  | ------------------ | ------ | ------------------------------------------------------------------------ |
  | `__apdb_meta__`    | `true` | Marker identifying this as the meta record, not a ticker record.        |
  | `format_version`   | number | On-disk format version. Currently always `1` (`DB_FORMAT_VERSION` in `src/database.rs`). |
  | `built_at_unix`    | number | Unix timestamp (seconds) captured when this compaction *started* — the authoritative "how old is this data" clock. |

  The meta record is rewritten fresh on every compaction; a stale meta line
  is never carried forward the way old ticker records are.

- **Line 1 onward — ticker records.** Identical to v0: one Polymarket event
  JSON object per line, keyed by `ticker`.

## Loading (`Snapshot::from_file`, `src/database.rs`)

The loader special-cases only the very first line read (byte offset `0`):
if it parses as JSON and has `"__apdb_meta__": true`, it's consumed as
metadata — `built_at_unix` and `format_version` are read from it, and the
line is **not** added to the ticker index, not counted in `lines`, and does
not trigger the "skipped bad/empty-ticker record" warning that a line
without a valid `ticker` would otherwise get. Every line after it is parsed
exactly as in v0.

If the first line does **not** look like a meta record (no `__apdb_meta__`
marker, e.g. a v0 file, or a v1 file with a corrupted line 0), nothing
special happens: `format_version` reports `0`, and `built_at_unix` falls
back to the file's mtime (then `now()` if that's unreadable) — the old v0
behavior, so v0 files keep loading unmodified.

## Freshness — a real TTL, not process-uptime sleep

`built_at_unix` is now what "freshness" means, both for API consumers and
for APDB's own boot logic (`src/main.rs`), and it no longer depends on
filesystem mtime (see v0's problems with that) or on how long the process
has been running.

At boot, with `POLYMARKET_FULL_MARKET_CACHE_REFRESH_INTERVAL` acting as the
TTL:

```
age = now - snapshot.built_at_unix

if age < interval:
    serve the loaded snapshot immediately
    first background refresh fires after (interval - age)
else:
    do NOT serve the stale snapshot
    run full_crawl_and_compact synchronously, before accepting connections
      (old snapshot passed in as `old` for the never-evict merge)
    serve the freshly built snapshot instead
    first background refresh fires after the full interval
```

Every refresh after the first — background or the one-off startup refresh —
waits the full `interval` before the next cycle (`spawn_refresh_loop` in
`src/refresh.rs`).

Concretely, with a 16h interval: run the process, kill it, restart it 10
days later. Under v0 this would serve the 10-day-old file immediately and
wait up to another 16h before refreshing. Under v1, boot detects the
snapshot is 10 days old — past the 16h TTL — and blocks on a fresh crawl
before the server starts accepting connections at all, then resumes the
normal 16h cadence from that point.

## Exposed via the wire API

`db_info` (`src/api.rs`) reports both fields from the currently served
snapshot:

```json
{ "result": { "built_at_unix": 1755000000, "db_format_version": 1, ... } }
```

## Compatibility

Reading is unconditionally backward compatible with v0 (see Loading,
above) — no migration step, no format flag to set. A v0 file simply reports
`format_version: 0` and uses mtime-derived age until the next compaction
(background refresh, or the stale-at-boot refresh) rewrites it with a v1
meta line, after which it's a v1 file.

There's no forward compatibility: a v0 build reading a v1 file sees the
meta line as an ordinary record with a missing/empty `ticker`, logs it as a
"skipped record" warning, and otherwise loads the rest of the file fine.
Harmless, but noisy — don't run a v0 binary against a v1 file in production
if avoidable.
